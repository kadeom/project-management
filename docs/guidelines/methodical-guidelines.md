# 1. Общие положения

Методические указания описывают единый учебный комплект по моделированию проекта в
Microsoft Project. Комплект состоит из четырёх частей:

- лабораторные работы 1–9 — обязательный минимум по MS Project;
- самостоятельная работа студента (SIW — student independent work) — дополнительные
  задания к каждой лабораторной работе;
- дополнительные задания 10 и 12 — практические работы по внедрению средств защиты
  информации (PAM и DLP + SIEM);
- управленческие артефакты проекта — устав, реестр заинтересованных сторон, СДР,
  RACI, реестр рисков, планы качества и коммуникаций, журнал изменений, отчёты о
  статусе и завершении.

Все числовые данные, задачи, ресурсы, ставки и календарь хранятся в одном файле
`project.yaml`. Тексты отчётов и методических документов не должны дублировать числа:
их берут из модели при сборке.

## 1.1. Цель дисциплины

Сформировать практические умения:

- формулировать цель, границы и критерии успеха проекта;
- строить СДР и календарный план, назначать ресурсы и стоимость;
- анализировать критический путь, перегрузки, риски и отклонения;
- готовить управленческую документацию и защищать решения перед заказчиком.

## 1.2. Результаты обучения

| Результат | Как проверяется |
|---|---|
| Строит план проекта в MS Project | XML/MPP-файлы, скриншоты, устная защита |
| Считает сроки, стоимость и PERT | `analysis.md`, `expected.json`, сверка с MS Project |
| Управляет ресурсами и перегрузками | лист ресурсов, графики загрузки, сценарии выравнивания |
| Оформляет управленческие документы | устав, реестр рисков, RACI, отчёты |
| Обосновывает решения | выводы, ответы на контрольные вопросы |

- **Команда** — выполняет работы, ведёт оценки и сообщает о рисках.
- **Куратор** — проверяет методическую корректность и допускает к защите.

# 4. Единая модель проекта

## 4.1. Что хранится в `project.yaml`

- метаданные: название, короткий код, автор, дата старта, валюта, репозиторий;
- календарь: рабочие часы и исключения;
- ресурсы: трудовые, материальные и затратные, ставки A/B, доступность;
- коды структуры: коды работ и коды отделов;
- фазы и задачи: длительность, PERT-оценки, связи, ресурсы, ограничения, крайние сроки,
  заметки и гиперссылки.

## 4.2. Команды сборки

```bash
python build_all.py              # весь комплект без XML/Java
python build_all.py --xml        # + XML MSPDI (Java 8+)
python build_all.py --full       # + .mpp и скриншоты (Windows + MS Project)
```

Отдельные генераторы:

```bash
python build.py                  # ЛР1–9: XML, расчёты, отчёт
python build_siw.py              # СРС (SIW): out/siw-report.docx
python build_infosec.py          # ДЗ 10/12: .md, .docx, XML
python build_guidelines.py       # эти методические указания → .docx
```

## 4.3. Правило одного источника

Запрещено вручную править файлы в `out/`: они пересобираются. Если нужно изменить
задачу, ресурс, ставку или календарь — правьте `project.yaml`, затем запускайте сборку.
Исключение — отчёт со скриншотами: он собирается из шаблона и снимков экрана.

# 5. Самостоятельная работа студента (SIW)

СРС расширяет лабораторные работы заданиями, которые требуют отдельного учебного файла
или дополнительного анализа. Источник заданий — `siw/siw.yaml`; отчёт собирает
`build_siw.py`. В именах файлов, каталогов и ID снимков используется сокращение **SIW**
(student independent work), в русском тексте допускается «СРС».

## 5.1. Состав СРС

| ЛР | Задание | Артефакт |
|---|---|---|
| 1 | Три встроенных календаря; учебный проект с двумя исключениями | два снимка, отдельный `.mpp` |
| 2 | Учебный файл из 10 задач; повторяющаяся задача | снимок связей и формы повторения |
| 3 | Типы задач; профили загрузки | таблица «что изменилось», снимки |
| 4 | СДР из четырёх уровней; заметка, ссылка, OLE | снимки маски и индикаторов |
| 5 | Таблицы норм затрат A/B и дата действия | снимок ставок и затрат |
| 6 | Доступность ресурса и пиковые нагрузки | лист ресурсов, график ресурсов |
| 7 | Выравнивание и его влияние на срок | снимки до/после, таблица сравнения |
| 8 | Поля Длительность1–4; веса PERT; крайний срок | снимки полей и индикатора |
| 9 | Пять сценариев сокращения; стоимость по кодам | таблица сценариев, группировка |

## 5.2. Порядок выполнения СРС

1. Соберите базовый план: `python build.py`.
2. Откройте XML или `.mpp` в MS Project.
3. Выполните задания по порядку, сохраняя промежуточные файлы с префиксом `siw_`.
4. Снимайте экран в точках, указанных в задании; ID снимка — `siw_lrN_KK`.
5. Соберите отчёт: `python build_siw.py`.
6. Вставьте снимки: `python -m automation.fill_report --src out/siw-report.docx --dst out/siw-report-final.docx`.
7. Проверьте чек-лист из раздела 3 отчёта и ответьте на контрольные вопросы.

## 5.3. Критерии СРС

- задание выполнено в отдельном файле, базовый план не испорчен;
- снимок подтверждает именно то действие, которое требуется;
- вывод содержит числа: срок, стоимость, количество перегрузок или задач;
- объяснена причина эффекта, а не только констатирован результат.

# 6. Лабораторные работы 1–9

Каждая работа завершается артефактом и защитой. Полный пошаговый чек-лист — в
`docs/guides/checklist.md`; ниже — цель, результат и контрольные вопросы.

## 6.1. ЛР1. Основы планирования

**Цель:** создать проект, настроить календарь и понять, как исключения влияют на сроки.

**Артефакт:** `out/01_plan_lab1-2.xml`, `out/01_plan_lab1-2.mpp`.

**Контрольные вопросы:**

- чем «планирование от даты начала» отличается от планирования от даты окончания;
- как исключение календаря влияет на длительность и окончание;
- для каких проектов подходит календарь «24 часа», а для каких — «Ночная смена».

## 6.2. ЛР2. Задачи, связи, ограничения

**Цель:** построить структуру «сверху вниз», освоить типы связей, вехи, ограничения и
крайние сроки.

**Артефакт:** тот же план; таблица связей и диаграмма Ганта.

**Контрольные вопросы:**

- чем ограничение отличается от крайнего срока;
- что происходит с задачей при жёстком ограничении и отрицательном резерве;
- зачем нужны вехи и как они связаны с фазами.

## 6.3. ЛР3. Ресурсы и назначения

**Цель:** ввести трудовые, материальные и затратные ресурсы, назначить их и проверить
доступность.

**Артефакт:** `out/02_full_lab3-7_9.xml`; лист ресурсов и назначения.

**Контрольные вопросы:**

- как тип задачи влияет на добавление второго исполнителя;
- что означают «Макс. единиц» и «Пиковая нагрузка»;
- чем материальный ресурс отличается от затратного.

## 6.4. ЛР4. СДР, заметки, гиперссылки

**Цель:** настроить коды СДР, добавить заметки, ссылки и связанные объекты.

**Артефакт:** XML/MPP с кодами, заметками и ссылками; снимки индикаторов.

**Контрольные вопросы:**

- как маска кода СДР влияет на нумерацию;
- чем заметка отличается от гиперссылки;
- почему OLE-объект нельзя надёжно передать через XML.

## 6.5. ЛР5. Стоимость проекта

**Цель:** рассчитать стоимость по ставкам, фиксированным затратам и таблицам A/B.

**Артефакт:** таблица затрат, денежный поток, `out/analysis.md`.

**Контрольные вопросы:**

- как дата действия ставки влияет на стоимость;
- чем отличаются способы начисления «в начале», «в конце» и «пропорционально»;
- почему итоговая стоимость не меняется при смене способа начисления.

## 6.6. ЛР6. Доступность ресурсов

**Цель:** найти перегрузки и объяснить, как их измеряет MS Project.

**Артефакт:** лист ресурсов, график ресурсов, таблица перегрузок.

**Контрольные вопросы:**

- как периоды доступности 50/0/100 % влияют на пиковую нагрузку;
- почему кратковременная перегрузка не видна при детализации «по неделям»;
- какие ресурсы перегружены и почему.

## 6.7. ЛР7. Выравнивание загрузки

**Цель:** применить выравнивание и оценить его влияние на сроки и стоимость.

**Артефакт:** план до/после, диаграмма Ганта с выравниванием, вывод.

**Контрольные вопросы:**

- почему автоматическое выравнивание может удлинить проект;
- когда лучше заменить ресурс, а когда — сдвинуть задачу;
- что происходит с критическим путём после выравнивания.

## 6.8. ЛР8. PERT-анализ

**Цель:** оценить неопределённость длительности через три оценки и веса.

**Артефакт:** `out/03_pert_input_lab8.xml`, `out/04_pert_result_lab8.xml`, таблица PERT.

**Контрольные вопросы:**

- почему в Project 2010+ нет панели PERT;
- как формула 1-4-1 меняет ожидаемую длительность;
- что означает стандартное отклонение критического пути.

## 6.9. ЛР9. Критический путь и стоимость

**Цель:** найти критический путь, проверить сценарии сокращения и разложить стоимость.

**Артефакт:** XML/MPP с кодами и полями стоимости, таблица сценариев, вывод.

**Контрольные вопросы:**

- какие задачи критические и почему;
- какой сценарий сокращения даёт наибольший эффект;
- как распределены затраты по кодам работ и отделов.

# 8. Управленческие артефакты проекта

Помимо расписания, комплект должен содержать документы, которые требуют ГОСТ Р 54869-2011
и практика управления проектом. Шаблоны лежат в `docs/artifacts/templates/`.

| Артефакт | Минимальное содержание | Критерий |
|---|---|---|
| Устав проекта | цель, границы, допущения, ограничения, критерии успеха, роли | цель измерима, границы явные |
| Реестр заинтересованных сторон | сторона, интерес, влияние, отношение, действие | все ключевые стороны учтены |
| Словарь СДР | код, работа, результат, ответственный, критерий приёмки | каждый пакет работ имеет результат |
| RACI-матрица | задача × роль, R/A/C/I | один A на задачу, нет пустых строк |
| Реестр рисков | риск, вероятность, влияние, оценка,реагирование, владелец | есть топ-5 и план реагирования |
| План качества | объект контроля, метрика, метод, периодичность | метрики измеримы |
| План коммуникаций | кому, что, когда, в каком формате, кто отвечает | покрыты все заинтересованные стороны |
| Журнал изменений | дата, изменение, причина, влияние, решение | каждое изменение прослеживается |
| Отчёт о статусе | период, план/факт, отклонения, риски, решения | есть вывод и следующее действие |
| Отчёт о завершении | результат, приёмка, уроки, архив | результат принят заказчиком |

Требования к оформлению:

- титульный лист, версия, дата, автор;
- таблицы с заголовками и единицами измерения;
- ссылки на источники для внешних утверждений;
- отсутствие персональных данных и реальных коммерческих тайн.

# 9. Порядок выполнения и сдачи

## 9.1. Рекомендуемый порядок

1. Заполнить `project.yaml`: метаданные, календарь, ресурсы, задачи.
2. Собрать XML и расчёты: `python build.py`.
3. Открыть XML в MS Project, выполнить ручные шаги из чек-листа.
4. Снять скриншоты и сохранить `.mpp`.
5. Выполнить СРС: `python build_siw.py`, снимки `siw_*`.
6. Собрать два ДЗ: `python build_infosec.py`.
7. Подготовить управленческие артефакты по шаблонам.
8. Собрать итоговый комплект: `python build_all.py --full`.
9. Проверить чек-лист сдачи и защитить работу.

## 9.2. Что входит в сдачу

- XML и `.mpp` по ЛР1–9;
- отчёт по ЛР со скриншотами;
- отчёт по СРС (SIW) со скриншотами;
- два отчёта по ДЗ 10/12 и их XML/MPP;
- управленческие артефакты (устав, реестр рисков, RACI и др.);
- презентация или устные ответы по контрольным вопросам.

## 9.3. Запрещено

- вручную править файлы в `out/` вместо `project.yaml`;
- подгонять числа в отчёте под MS Project без объяснения расхождения;
- сдавать скриншоты без подписи и ID;
- использовать реальные персональные данные и коммерческую тайну.
